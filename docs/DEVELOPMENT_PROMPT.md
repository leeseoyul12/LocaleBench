# LocaleBench 고품질 웹서비스 개발 마스터 프롬프트

작성일: 2026-10-12, 한국 시간.
기준 문서: `이서율_Google_API_수행평가_후보검증_2026-10-07.md`.

사용법: 아래 「개발 에이전트에게 전달할 프롬프트」부터 끝까지 개발 에이전트에게 전달한다. 기준 문서를 같은 작업 폴더에 두거나 함께 첨부한다. 이 파일은 개발 실행 지시문이며, 파일 작성 자체가 제품 개발·API 연결·배포 완료를 의미하지 않는다.

## 개발 에이전트에게 전달할 프롬프트

너는 LocaleBench의 제품 설계, 프런트엔드, 백엔드, 데이터 모델링, 테스트, Git 관리, 외부 서비스 설정, 배포를 끝까지 담당하는 개발 에이전트다.

지금부터 계획을 설명하는 데 그치지 말고 실제 파일을 만들고 코드를 실행해 제품을 완성하라. 사용자는 개발 과정을 직접 지휘하거나 코드를 복사해서 조립하지 않는다. 통상적인 기술 선택, 설치, 구현, 오류 수정, 검증, 로컬 커밋은 네가 판단하고 수행한다.

기준 문서를 먼저 읽고 LocaleBench 관련 근거, MUST HAVE, PoC 통과 조건, 제외 범위, 시연 요구를 개발 기준으로 삼아라. 문서는 후보 검증과 실험 설계이며 실제 구현·성능 검증의 증거가 아니다. 기존 문서를 고쳐서 미실행 작업을 완료한 것처럼 만들지 마라.

### 1. 목표와 제품 정의

LocaleBench는 **번역 JSON을 정해진 UI 크기와 폰트로 렌더링해 문자열 넘침과 변수 오류를 찾고, 수정 전후를 같은 조건에서 비교하는 검사 작업공간**이다.

대상은 작은 웹 프로젝트에서 다국어 버튼, 라벨, 한줄 배너를 관리하는 개발자다. 핵심 사용자 흐름은 다음과 같다.

1. 프로젝트 생성 또는 샘플 프로젝트 열기.
2. 원본 flat JSON 입력·파일 가져오기와 입력 검증.
3. 대상 언어 선택과 변수 보호를 적용한 Google 번역.
4. 문자열별 컴포넌트, 폭, 폰트, 글자 크기, 변수 예시 값 지정.
5. 실제 브라우저 DOM 측정과 오류 탐색.
6. 번역 또는 fixture 조건 수정.
7. 동일 조건 재검사와 이전 실행 비교.
8. 번역 JSON·검사 보고서 내보내기와 프로젝트 재방문.

Google API는 실제 다국어 테스트 입력을 만드는 역할이다. DB는 프로젝트별 검사 조건, 번역 버전, 실행 결과, 해결 이력을 다음 검사에 재사용하는 역할이다. 각각 제품 흐름에서 사용되어야 한다.

번역 정확도 자동 보증, 임의 웹사이트 전체 검사, 실제 앱 CSS 완전 재현, 경쟁 제품보다 우수하다는 주장을 하지 않는다. 제품 설명은 ‘지원하는 fixture 조건의 넘침·변수 무결성 검사’로 구체화한다.

### 2. 자율 실행과 사용자에게 남기는 일

사용자가 이미 다음 작업을 맡겼다. 매 단계마다 ‘진행할까요?’라고 묻지 말고 필요한 작업을 수행하라.

- 기존 작업·저장소 상태 조사와 프로젝트 생성.
- 프로젝트 범위의 의존성 설치, 코드 작성, 실행, 테스트, 수정.
- DB 스키마·마이그레이션·샘플 데이터·소유권 정책 작성.
- Google Translation 연동 코드, 사용량 제한, 설정 확인 도구 작성.
- 로컬 Git 저장소 초기화가 필요한 경우 초기화와 의미 있는 단계별 커밋.
- 확인된 사용자 소유 개발 저장소의 작업 브랜치 push와 초안 PR 생성.
- 기존에 연결된 사용자 계정·CLI·커넥터로 가능한 개발 환경 설정.
- 사용자 소유 개발·프리뷰 환경의 배포와 배포 후 점검.
- 실행·설정·발표 문서와 재현 가능한 데모 완성.

외부 저장소·Cloud 프로젝트·배포 대상은 소유권과 용도를 먼저 확인한다. 이미 지정된 개발 대상은 재확인 없이 사용한다. 지정되지 않은 새 원격 저장소는 사용자 소유 계정이 확인되면 비공개 개발 저장소로 만들 수 있다. 이름 충돌 시 기존 저장소를 덮어쓰지 않는다. 외부 대상이 여러 개여서 선택이 필요하면 그 대상만 질문하고 로컬 개발을 계속한다.

운영 환경 덮어쓰기, 저장소 공개 전환, 유료 플랜 가입, 결제수단 등록, 새로운 유료 과금 연결, 기존 사용자 데이터 삭제는 일반 개발 작업과 구분한다. 이런 실제 변경이 필요할 때만 대상·이유·영향을 짧게 설명하고 필요한 결정을 요청한다. 새 계정의 약관 동의와 본인 확인은 사용자가 수행한다.

API는 가능한 범위에서 직접 설정하라. 사용 가능한 인증 세션이 있고 권한이 확인되면 지정된 개발 프로젝트에서 API 활성화·제한 설정·개발용 자격증명 준비를 수행한다. 권한이 없으면 권한을 우회하거나 타인의 키를 찾지 않는다.

사용자의 로그인이 필요하거나 키 발급·본인 확인·과금 승인만 사용자가 할 수 있다면, **그 직전까지 구현과 준비를 끝낸 뒤 필요한 사용자 작업만 남겨라.** 키가 없다는 이유로 파일 작성·테스트·DB 준비·로컬 데모·Git 작업을 중단하지 않는다.

사용자에게 남길 요청에는 다음 정보를 포함한다.

- 준비된 기능과 해당 키가 연결될 위치.
- 정확한 콘솔 링크와 수행할 최소 단계.
- 사용할 기존 프로젝트 ID 또는 사용자가 선택해야 할 대상.
- 환경변수 이름, 로컬 파일 위치, 배포 환경의 설정 위치.
- API 제한, 지원되는 애플리케이션 제한, 확인할 사용량 설정.
- 키 설정 후 네가 실행할 연결 확인 명령.

비밀값은 채팅에 붙여넣도록 요구하지 않는다. 로컬 비공개 환경변수 파일 또는 배포 서비스의 secret 설정에 사용자가 입력하게 하고, 입력 완료 사실만 받는다. 키가 제공되면 실제 호출·배포 검증·문서 갱신까지 이어서 수행한다.

사용자가 직접 해야 할 일이라는 이유로 전체 설정 문서를 넘겨서 나머지 구현을 맡기지 마라. 자동 실행 가능한 작업은 네가 하고, 실행 불가능한 작업은 바로 실행할 수 있는 스크립트·설정 파일과 짧은 안내로 준비한다.

### 3. 첫 작업: 작업 폴더와 개발 환경 조사

현재 폴더의 기준 md, 적용되는 `AGENTS.md`, 기존 코드, Git 상태를 확인하라. 기존 사용자 수정은 보존한다. 일반 문서의 ‘완료’ 표현을 실제 코드 상태로 추정하지 않는다.

Node.js, 패키지 관리자, Git, 사용 가능한 브라우저 테스트 환경, 외부 서비스 CLI의 존재를 확인한다. 자격증명 값은 출력하지 않고 설정 유무·인증 상태만 확인한다. 도구가 PATH에 없으면 통상 설치 경로를 확인하고, 없으면 프로젝트 작업에 필요한 도구를 안전한 사용자 범위로 준비한다. 공유 PC 전체 설정을 불필요하게 바꾸지 않는다.

이미 앱이 있으면 그 구조에 맞춰 개선한다. 이 문서만 있는 폴더라면 `localebench/` 하위 폴더에 앱을 만들고 기준 문서를 보존한다. 상위 Git 저장소가 있다면 불필요한 중첩 저장소를 만들지 않는다.

작은 작업 계획과 완료 기준을 기록한 뒤 바로 기술 PoC를 시작한다. 긴 기획서부터 만들거나 화면 전체를 먼저 꾸미지 않는다.

### 4. 기술 선택

새 프로젝트의 기본 후보는 다음과 같다. 기존 프로젝트와 실행 환경에 맞게 선택하되 이유를 짧게 기록한다.

- Next.js, TypeScript, 서버 Route Handler.
- Tailwind CSS와 필요한 접근성 컴포넌트만 사용.
- Cloud Translation Basic v2의 표준 NMT 번역을 서버에서 호출.
- Supabase Auth와 PostgreSQL을 클라우드 영속 저장소로 사용.
- 핵심 도메인 함수 단위 테스트와 Playwright 브라우저 테스트.
- 서버 환경변수를 지원하는 개발·프리뷰 배포 환경.

버전은 구현 시점 공식 문서와 호환성을 확인하고 안정 버전으로 고정한다. 기존 스택이 합리적이면 불필요하게 갈아엎지 않는다. 패키지 lockfile을 저장한다. 서버 비밀을 보호할 수 없는 순수 정적 배포를 실제 Google 연동 배포라고 제시하지 않는다.

MVP에 Gemini, 별도 AI 채팅, 여러 DB 제품, 협업 인프라, 백그라운드 큐를 추가하지 않는다. 배포 플랫폼과 DB 제품을 늘리는 것은 실제 요구를 해결할 때만 한다.

### 5. 가장 먼저 수행할 기술 PoC

원본 문서의 45분 기술 스파이크를 먼저 재현하라. 45분은 조사용 가이드이며 시간이 지났다는 이유로 미검증 구현을 통과시키지 않는다.

- 직접 작성한 flat JSON 문자열 10개.
- 버튼·라벨·한줄 배너의 지원 fixture.
- 원본 언어 `en`, 대상 언어 `de`, `fr`, `ko`.
- 폭 100/160/240px, 고정 폰트 2개.
- 10문장 × 3대상 언어 × 3폭 × 2폰트 = 180개 렌더 케이스.
- `{name}`, `%s`, 같은 변수가 반복되는 사례, 변수가 없는 사례.
- 정상 문장, 명백히 긴 문장, 변수 누락·추가·변형을 주입한 사례.

렌더 케이스 수와 개별 오류 주입 테스트 수는 구분해 기록한다. 180개를 실제 실행하지 않았다면 실행했다고 쓰지 않는다.

통과 기준은 다음과 같다.

1. 지원 변수의 마스킹·복구·개수 검증이 오류 주입 테스트에서 모두 정확하다.
2. 사전에 정상·넘침을 정한 golden fixture를 실제 브라우저에서 검사해 모두 일치한다.
3. 폰트 로드 후 같은 조건을 재검사해 판정이 안정적이다.
4. 폰트 로드 실패·숨겨진 요소·측정 불가를 ‘정상’으로 처리하지 않는다.
5. Google 비밀키가 클라이언트 번들·로그·커밋에 포함되지 않는다.

API 키가 있으면 실제 Google 번역으로 마스킹을 검증한다. 키가 없으면 직접 작성한 명시적 데모 번역과 mock provider로 로컬 검증을 수행한다. mock 성공을 실제 Google의 토큰 보존 성공으로 계산하지 않는다. PoC 보고서에 ‘로컬 통과 / 실제 API 검증 대기’를 따로 기록한다.

로컬 핵심 검사가 통과하면 UI와 저장 기능을 계속 개발해 사용자 키 입력만 남기는 단계까지 완성한다. Google 연동의 완료 표시는 실제 호출을 통과한 뒤에만 한다. PoC가 실패하면 지원 문법·컴포넌트를 좁혀 고친다. LocaleBench의 핵심이 성립하지 않을 때 결과와 재현 사례를 남기고 사용자의 결정이 필요한 부분만 질문한다. 임의로 BookSpec 등 다른 제품을 개발하지 않는다.

### 6. 입력과 변수 무결성

flat JSON은 최상위 객체의 문자열 키와 문자열 값만 허용한다. 배열, 중첩 객체, 숫자 값, null, 잘못된 JSON, 충돌하는 키는 키·위치·수정 방법을 포함해 안내한다. 중복 키가 파싱 과정에서 조용히 덮어써지지 않도록 검사한다. 한글·이모지·따옴표·백슬래시를 보존한다.

초기 제한은 프로젝트당 100문자열, 문자열당 2,000 Unicode 코드 포인트, 요청 본문 256KiB, 최대 3대상 언어로 두고 서버에서 강제한다. 일일 번역 한도는 별도 설정한다. 실제 API의 측정 단위·요청 한도와 대조해 보수적으로 조정한다.

지원 변수 문법을 작은 명세로 고정하고 파서와 테스트를 만든다.

- `{name}` 형태의 단순 named placeholder.
- `%s` 형태의 positional placeholder.
- `%%`를 literal percent로 처리하는 규칙.
- named placeholder의 이름별 등장 횟수 비교.
- positional placeholder의 개수와 순서 의미 유지.
- 지원하지 않는 ICU plural·select·복잡한 중괄호·HTML은 명확하게 거부.

문자열 정규식 하나로 모든 문법을 지원한다고 주장하지 않는다. 단순 brace 문법, literal brace의 허용 여부, escape 처리를 문서화한다.

각 placeholder 발생 위치에 충돌 없는 토큰을 배정하고 번역 후 복구한다. 원문에 토큰과 같은 문자열이 있는 경우도 검사한다. 번역 과정에서 토큰이 누락·변형·추가·중복되면 변수 오류로 처리한다. 번역 서비스가 토큰을 항상 보존한다고 가정하지 않는다.

명명된 변수의 문장 내 이동과 이름·개수 훼손을 구분한다. `%s`만으로 여러 변수의 의미 순서를 보장할 수 없는 사례는 지원 범위 밖 또는 검토 필요로 표시한다. 오류가 발생한 번역을 정상 결과로 저장·내보내지 않는다. 필요하면 수동 번역 수정 경로를 제공한다.

fixture에 넣을 `{name}` 예시 값은 기본값과 사용자 입력값을 저장한다. **변수 무결성은 원문 템플릿에서 검사하고, 화면 폭은 예시 값을 치환한 문장에서 측정한다.** 보고서에 사용한 예시 값을 남긴다.

### 7. Google Translation 실제 연동

브라우저는 자체 서버만 호출하고, 서버가 Google 번역을 호출하게 하라. v2를 v3 API 키 방식과 혼동하지 않는다. 공식 문서에서 현재 인증·요청·응답·과금 단위를 확인하고 구현한다.

provider 인터페이스를 정의해 Google provider와 명시적 demo/mock provider를 바꿀 수 있게 한다. mock provider는 자동 테스트에서 실제 요금을 발생시키지 않는다. 실제 API 실패 시 mock 결과로 몰래 바꾸지 않는다.

- 입력 검증, 사용자 인증·프로젝트 소유권 검사를 먼저 수행.
- 허용 언어 목록과 요청당 문자열·언어·문자 수 제한.
- `format: text` 등 실제 지원되는 plain-text 요청 사용.
- 응답 개수·순서·자료형·변수 토큰 검증.
- 빈 응답, 잘못된 응답, 인증 오류, API 비활성화, 과금 미설정, 429, 시간 초과 구분.
- 제한된 재시도와 요청 시간 제한. 무한 재시도 금지.
- 동일 요청 중복 실행 방지와 조건이 일치하는 번역 캐시.
- 서버리스 인스턴스 간에도 효력이 있는 사용자·전체 문자 사용량 제한.
- 동시 요청에 대한 원자적 사용량 예약으로 한도 우회 방지.
- 실제 청구 가능성이 있는 재시도·취소를 고려한 사용량 기록.

`.env.example`에는 `GOOGLE_TRANSLATION_API_KEY` 같은 이름과 빈 예시만 둔다. Google 비밀키에 `NEXT_PUBLIC_` 접두사를 사용하지 않는다. Supabase의 공개 publishable key는 RLS와 함께 사용하는 공개 설정임을 비밀키와 구분한다. service-role·secret key는 브라우저에 보내지 않는다.

Google 공식 보안 권고에 맞춰 지원되는 방식으로 비밀키를 전달한다. 가능하면 URL 대신 지원되는 요청 헤더를 사용한다. URL 기반 인증이 필요한 경우 URL 전체가 로그에 남지 않도록 처리한다. 외부 오류 객체에 포함된 키·헤더·토큰을 정리한다.

API 제한은 Translation에 필요한 서비스로 한정한다. 애플리케이션 제한은 실제 서버 실행 환경과 호환되는 제한을 선택한다. 서버용 키에 브라우저 referrer 제한을 무조건 적용하거나, 고정 egress IP가 없는 환경에 임의 IP 제한을 적용하지 않는다. 환경 제약과 대안을 설정 문서에 남긴다.

과거 무료량·요금·quota를 현재 값으로 복사하지 않는다. 확인한 공식 링크와 날짜를 기록하고, 콘솔의 프로젝트별 값과 앱 자체 한도를 구분한다. 예산 알림을 강제 과금 차단 장치라고 설명하지 않는다.

### 8. 실제 DOM 측정

컴포넌트는 버튼, 라벨, 한줄 배너 3개만 지원한다. 각 fixture에 실제 CSS 규칙과 폭의 정의를 고정한다. 외곽 폭, padding, border, 텍스트가 사용할 수 있는 내부 폭을 혼동하지 않는다.

측정은 브라우저에서만 수행한다. 글자 수·평균 글자 폭·서버 추정값을 실제 측정처럼 제시하지 않는다.

1. 로컬에 고정된 폰트 파일과 글꼴 이름을 준비한다. 폰트 라이선스·버전을 기록한다.
2. 해당 폰트 로드와 `document.fonts.ready`를 기다리고 실제 적용을 확인한다.
3. fixture를 레이아웃이 계산되는 상태로 렌더링한다. `display:none` 상태를 측정하지 않는다.
4. 필요한 animation frame을 기다린 뒤 텍스트와 컨테이너를 측정한다.
5. `scrollWidth/clientWidth`, 필요한 경우 `scrollHeight/clientHeight`와 텍스트 bounding box를 함께 해석한다.
6. 소수점·반올림 허용 오차를 정의하고 경계값 테스트로 검증한다.
7. 문자열·변수 예시·폭·폰트가 바뀌면 이전 결과를 오래된 것으로 표시하고 재측정한다.

컨테이너 폭을 매번 텍스트 길이에 맞춰 늘리거나 자동 폰트 축소해 넘침을 숨기지 않는다. 검사 preview는 실제 잘림을 보여주고, 별도의 전체 문장 보기와 수치로 원인을 설명한다.

실측 조건에는 컴포넌트 타입, 폭, padding, font family·version, font size·weight, letter spacing, line-height, 변수 예시, 브라우저·viewport·device pixel ratio, 측정 엔진 버전을 저장한다. 조건이 달라진 실행은 동일 조건 비교와 구분한다.

폰트 로드 실패나 브라우저 지원 범위 밖은 측정 불가로 처리한다. 지원 범위 밖의 임의 CSS·사용자 React 코드·원격 URL을 실행하지 않는다.

### 9. UI와 사용 경험

한국어 중심의 정돈된 개발 도구 UI를 만들고 브랜드명은 LocaleBench로 유지한다. 설명은 사용자가 지금 무엇을 입력하고 어떤 오류를 고칠지 이해하게 작성한다. 구현 내부 용어를 모든 화면에 늘어놓지 않는다.

기본 시각 방향은 밝은 중립 배경, 읽기 쉬운 짙은 텍스트, indigo 계열 강조색, 오류·주의·정상의 절제된 상태색이다. 실제 데이터 테이블과 검사 preview가 화면의 중심이어야 한다. 대형 홍보 히어로·과도한 그라데이션·장식 애니메이션보다 작업 밀도와 가독성을 우선한다.

주요 화면은 다음과 같다.

- 프로젝트 목록: 최근 프로젝트, 마지막 검사 상태, 샘플 시작.
- 프로젝트 작업공간: 문자열 목록·검색·필터, 편집 영역, fixture preview.
- 결과 보기: 오류 종류·언어·문자열별 필터와 측정 근거.
- 실행 비교: 새 오류, 지속 오류, 해결, 조건 변경 또는 비교 불가.
- 설정: 기본 언어·fixture, 실제 연결 상태, 사용량.

데스크톱에서는 목록·편집·preview를 동시에 보기 좋게 배치하고, 작은 화면에서는 탭·패널 전환으로 자연스럽게 축소한다. 360px·768px·1440px에서 제품 UI의 잘림과 가로 넘침을 점검한다. 검사 대상 fixture의 의도된 넘침과 서비스 자체 UI 결함을 구분한다.

필수 상태를 구현한다: 첫 실행, 빈 프로젝트, JSON 오류, 번역 중, API 미설정, 번역 실패, 부분 실패, 폰트 실패, 검사 중, 결과 없음, 저장 중, 저장 실패, 오래된 측정 결과, 재검사 완료.

문자열 수정은 임시 저장·저장 상태를 명확히 보여준다. 같은 버튼을 연타하면 중복 API 요청이 생기지 않게 한다. 실패 후 입력을 잃지 않고 다시 실행할 수 있어야 한다.

아이콘만으로 상태를 전달하지 않는다. 키보드 탐색, 보이는 focus, form label, 상태 텍스트, 적절한 대비, 오류 영역 이동을 제공한다. 실제 기능이 없는 버튼과 가짜 통계를 만들지 않는다.

### 10. 키 없이 실행되는 로컬·데모 경로

외부 키가 없을 때도 앱을 실행하고 전체 핵심 흐름을 검증할 수 있어야 한다.

- 직접 작성한 원본 JSON과 언어별 데모 번역 데이터.
- 명시적인 ‘데모 데이터 사용’ 표시.
- 동일한 실제 브라우저 DOM 측정과 변수 검증.
- 원본·번역 수정, fixture 변경, 재검사, 실행 비교, export.
- 브라우저 IndexedDB 등으로 새로고침 후 유지되는 로컬 프로젝트·실행 이력.
- 클라우드 연결과 로컬 저장의 상태를 별도로 표시.

이 로컬 경로는 실제 클라우드 DB 구현이나 Google 호출을 대체하는 완료 증거가 아니다. 공통 도메인 타입과 작은 저장소 인터페이스로 관리하고 두 시스템을 중복 개발하지 않는다. 공개 데모 모드의 Google 호출은 기본적으로 비활성화한다.

Google 키만 없을 때는 수동 번역 입력으로 실측과 저장 기능을 계속 사용하게 한다. Supabase만 없을 때는 로컬 저장소를 사용한다. 실제 provider와 cloud repository 구현, 마이그레이션, 연결 점검은 별도로 준비한다.

### 11. 데이터 모델과 실행 비교

다음 논리 엔터티를 정규화해 구현한다. 이름은 프로젝트 관례에 맞게 바꿀 수 있으나 관계와 의미를 보존한다.

| 엔터티         | 핵심 데이터                                                                         |
| -------------- | ----------------------------------------------------------------------------------- |
| projects       | id, owner_id, name, source_locale, created_at                                       |
| source_strings | project_id, key, source_text, placeholder_schema, revision                          |
| translations   | string_id, locale, text, provider, revision, validation_status                      |
| fixtures       | project_id, string_id, component_type, width, font 설정, 변수 예시, revision        |
| runs           | project_id, status, source·translation·fixture snapshot, engine_version, timestamps |
| measurements   | run_id, key, locale, fixture 식별자, 측정 수치, 측정 상태                           |
| findings       | run_id, 대상 식별자, kind, severity, 근거, 안정적인 비교 식별자                     |
| resolutions    | finding 식별자, 검토 상태, note, 확인한 run, timestamps                             |
| usage          | owner_id, 요청 식별자, 기간, 예약·사용 문자 수, 실행 상태                           |

원문·번역·fixture를 수정해도 과거 run의 snapshot과 결과를 바꾸지 않는다. 분석 중 수정된 입력과 측정 결과가 섞이지 않도록 revision 또는 snapshot hash를 확인한다.

run은 pending/running/completed/partial/failed 같은 상태를 갖고 부분 실패를 정상 완료로 표시하지 않는다. 저장에 실패한 결과는 저장된 것처럼 표시하지 않는다.

동일 조건 비교는 key·locale·fixture 조건·변수 예시·측정 엔진 등의 호환성을 확인한다. 바뀐 조건을 더 좋은 번역의 증거로 오인하지 않는다. fixture 폭을 넓혀 해결한 것과 번역 문장을 수정해 해결한 것을 구분해 보여준다.

사용자가 ‘해결됨’을 눌러도 재검사 결과에서 오류를 지우지 않는다. 검토 상태와 실제 검출 상태를 따로 보관하고 재발을 표시한다. 원문 변수 오류가 있는 export는 막거나 명확하게 오류를 전달하는 별도 진단 export로 분리한다.

Supabase를 사용하면 모든 사용자 데이터 테이블에 적절한 RLS를 적용한다. 클라이언트가 보낸 owner_id를 신뢰하지 말고 인증된 사용자에서 결정한다. 자식 테이블도 상위 프로젝트 소유권을 검사한다. 관계를 이용해 다른 사용자 프로젝트에 데이터를 삽입하지 못하게 한다. user A/B와 비인증 접근으로 조회·수정·삭제·삽입을 검증한다.

마이그레이션과 seed를 파일로 제공한다. 개발 테스트용 프로젝트를 대상으로 적용하고 기존 데이터가 있는 환경의 destructive reset은 실행하지 않는다. 삭제 기능은 소유권과 관계를 검사하고 프로젝트·번역 데이터 삭제 범위를 설명한다.

### 12. 서버 보안과 오류 처리

입력은 텍스트로 렌더링한다. `eval`, 사용자 제공 코드 실행, `dangerouslySetInnerHTML`, 무제한 파일 업로드, 사용자 URL 서버 fetch를 도입하지 않는다. HTML처럼 보이는 문자열도 브라우저에서 실행되지 않아야 한다.

서버가 인증·소유권·자료형·길이·언어·사용량 제한을 다시 검사한다. 프런트엔드 검증만으로 보호하지 않는다. mutation 요청의 인증 방식에 맞는 CSRF·Origin 처리를 마련한다. 사용량 저장소가 고장 나면 유료 API 호출을 무제한 허용하지 않는다.

오류 응답은 짧은 사용자 안내, 안정적인 오류 코드, 재시도 가능 여부를 제공한다. 로그에는 요청 식별자와 필요한 진단 정보만 남긴다. 원문 전체·Google 키·DB secret·세션 토큰을 자동으로 기록하지 않는다.

외부 설정을 확인하는 endpoint는 비인증 사용자에게 secret 존재·프로젝트 정보·환경변수 내용을 노출하지 않는다. CI·예제·스크린샷·보고서에도 비밀값을 넣지 않는다.

### 13. 테스트와 검증 증거

핵심 실패를 찾는 의미 있는 테스트를 작성하고 실제 실행하라. 테스트 이름만 나열하거나 아직 실행하지 않은 결과를 성공으로 보고하지 않는다.

**단위·서버 검증**

- flat JSON 중복 키·중첩·잘못된 값·길이 제한.
- named 변수 이동·중복·누락·추가, positional 변수와 literal percent.
- 토큰 충돌·번역 provider의 토큰 훼손.
- Google mock의 정상·401/403·429·시간 초과·응답 개수 오류.
- 동일 조건 판별, immutable run, 신규·지속·해결·재발 판정.
- 사용량 한도·동시 요청·중복 실행·실패 시 처리.

**실제 브라우저 검증**

- 폰트 로드 이후 실측과 로드 실패 처리.
- 명확한 정상·넘침 golden fixture와 경계값.
- 같은 글자 수라도 실제 폭이 다른 사례.
- 변수 예시 값에 따른 렌더 결과.
- 샘플 열기 → 오류 확인 → 수정 → 재검사 → 이전 run 비교.
- 새로고침 후 프로젝트·실행 이력 유지.
- HTML·script처럼 생긴 입력이 실행되지 않음.
- 대표 viewport에서 편집·결과·비교 화면 조작.

**클라우드 연결 검증**

- 실제 Google 작은 요청 1회와 변수 보호 사례, 사용량 기록.
- 실제 DB 저장·재조회·수정·삭제.
- 사용자 A/B 및 비인증 접근의 소유권 분리.
- 배포된 서버에서 번역·측정·저장·재조회 흐름.

실제 키가 없는 항목은 ‘미실행: 자격증명 필요’로 남기되 검증 스크립트를 완성한다. 자동 테스트는 기본적으로 유료 API를 호출하지 않으며 실제 호출 테스트는 명시적으로 분리한다.

타입 검사, lint, 핵심 테스트, production build를 프로젝트에 맞게 실행한다. build 성공만으로 제품 완료를 선언하지 않는다. Playwright 또는 사용 가능한 실제 브라우저로 주요 화면을 캡처하고 직접 열어 레이아웃·상태·사용 흐름을 확인한 뒤 결함을 수정한다.

PoC 보고서에는 케이스 수, 조건, 예상 판정, 실제 판정, 실패 사례, 실행 명령, 증거 파일을 남긴다. 실제 측정한 준비 시간만 기록한다. 경쟁 제품을 사용하지 않았다면 경쟁 우위 수치를 만들지 않는다.

### 14. Git과 개발 이력

Git이 없으면 통상 설치 경로를 확인한 뒤 필요한 범위에서 준비한다. 계정 인증이 없더라도 로컬 커밋은 진행한다. Git author는 기존 확인된 설정을 사용하고 사용자 이름·이메일을 만들어내지 않는다. author가 전혀 없으면 그 정보만 짧게 요청하고 나머지 개발은 계속한다.

브랜치명은 기존 관례가 없으면 `feat/localebench`를 사용한다. 의미 있는 단위로 커밋한다. 예시는 다음과 같다.

1. `chore: initialize LocaleBench workspace`
2. `feat: validate strings and measure supported fixtures`
3. `feat: integrate translation provider and usage limits`
4. `feat: persist projects and compare immutable runs`
5. `feat: complete workspace UI and demo flow`
6. `test: verify regression flow and prepare deployment`

순서와 개수는 실제 변경에 맞게 조정한다. 각 커밋 전에 diff와 비밀정보 포함 여부를 확인한다. 기준 md와 사용자 기존 변경을 실수로 수정하거나 stage하지 않는다. `git add .`로 모든 파일을 무조건 포함하지 않는다.

`.env`, 로컬 DB·개인 자료·대용량 테스트 출력은 적절히 ignore하고 `.env.example`, lockfile, schema, 필요한 샘플과 문서는 커밋한다. 이미 커밋된 secret을 발견하면 더 출력하거나 push하지 말고 영향과 키 교체 필요를 알려라.

확인된 개발 remote에는 작업 브랜치를 push할 수 있다. remote가 없거나 인증이 필요한 경우 로컬 커밋을 완료하고 그 단계만 대기로 기록한다. force-push, 기존 이력 삭제, 기본 브랜치 직접 덮어쓰기, 자동 merge는 하지 않는다. 초안 PR에는 문제·최종 동작·검증·남은 외부 연결 항목을 쓴다.

### 15. API·DB·배포 준비와 실제 연결

가용 CLI와 계정으로 수행 가능한 설정은 직접 실행한다. 불가능하면 다음 산출물을 실제로 준비한다.

- `.env.example`: 변수 목적·공개 여부·입력 위치 설명.
- 환경변수 확인 스크립트: secret 값 없이 누락된 이름과 오류만 출력.
- Google API 연결 점검: 작은 입력, 변수 보존, 응답 검증, 민감정보 제거.
- DB migration·seed·소유권 검증 도구.
- hosting 설정, build·start 명령, callback·Origin 설정.
- 배포 전 점검과 배포 후 smoke test 명령.
- 실행 가능한 플랫폼별 설정 절차와 키 입력 후 재개 지점.

새 Google 프로젝트 생성, API 활성화, 키 제한은 실제 권한·연결된 과금 상태를 확인해서 수행한다. 과금 연결 권한이 없으면 결제 정보를 대신 입력하지 않는다. Supabase 계정이 없으면 SQL과 인증 설정 안내를 완성한다. 수동 실행이 필요한 단계는 SQL·명령을 사용자가 다시 작성할 필요 없이 준비한다.

개발·프리뷰 배포 권한이 있으면 배포하고 HTTPS URL에서 전체 흐름을 점검한다. 외부 인증이 없더라도 로컬 production build·환경변수·배포 설정·점검 도구를 끝낸다. 배포 URL·API 연결·DB 저장을 성공했다고 표시하는 시점은 각각 실제 검증 후다.

사용자에게 작업을 넘기기 직전에 ‘준비 완료 / 실연결 완료 / 사용자 작업 필요’를 구분한다. 막힌 항목은 정확한 원인과 최소 조치를 쓰고, 아직 독립적으로 할 수 있는 작업은 먼저 끝낸다.

### 16. 실제로 만들어야 할 산출물

코드 외에 다음 문서를 간결하고 실행 가능하게 작성하라.

- `README.md`: 제품 정의, 설치·실행, 샘플 시작, 실제 연동, 지원 범위.
- `docs/architecture.md`: 브라우저 측정·서버 번역·DB 저장의 경계와 데이터 흐름.
- `docs/setup.md`: Google·Supabase·hosting 설정과 사용자가 해야 하는 최소 단계.
- `docs/poc-report.md`: 로컬 PoC와 실제 API 검증의 분리된 결과.
- `docs/test-report.md`: 실행 명령·성공/실패/미실행·증거 경로.
- `docs/demo-script.md`: 아래 150초 시연과 키 없는 대체 흐름.
- `docs/handoff.md`: 완료 작업, 외부 대상, 커밋, 남은 연결, 다음 실행 지점.
- `samples/`: 직접 작성한 원본·데모 번역·오류 주입 fixture·예상 판정.
- 마이그레이션, `.env.example`, lockfile, CI 설정, 필요한 setup·smoke scripts.

문서에 키·개인 정보·실제 사용자 원문을 넣지 않는다. 참조한 공식 문서에는 링크와 확인 날짜를 남긴다. 설명용 문서를 만들기 위해 개발과 검증을 미루지 않는다.

### 17. 150초 수행평가 시연

실제로 동작하는 샘플 프로젝트와 실행 이력을 준비하라.

- 0–20초: 프로젝트와 원본 10문장, 지원 범위 소개.
- 20–50초: 대상 언어 번역과 변수 보호 확인.
- 50–90초: 좁은 버튼의 실제 넘침과 변수 오류, 폰트·폭 근거 확인.
- 90–120초: 번역 수정과 동일 조건 재검사.
- 120–150초: 이전 run 비교, 해결·지속·새 오류, 저장 이력 확인.

Google 호출 결과와 직접 만든 오류 주입 사례를 구분한다. 번역 서비스가 실제로 변수를 잃지 않았다면 그것을 서비스 결함으로 꾸미지 말고 검사기를 검증하는 주입 사례로 설명한다.

실연결 시연이 어려울 때는 표시된 데모 데이터로 전체 검사 흐름을 보여주고 실제 API 상태를 밝힌다. ‘혼자 테스트’는 직접 만든 데이터의 정상·고장·수정 후 결과를 증거와 함께 설명한다.

평가자에게 설명할 내용을 짧게 준비한다: 해결하는 문제, Google API 역할, DB가 필요한 이유, 직접 구현한 검사, 변수 보호, 폰트 측정, API 키 보호, 경쟁 제품과의 범위 차이, 실제 테스트 결과와 한계.

### 18. 범위 제한

이번 버전에서는 전체 사이트 crawler, 임의 React 실행, 원격 CSS import, ICU plural·select, RTL 전체지원, 복잡한 다중행 레이아웃, AI 자동 디자인 수정, 브라우저 확장, 실시간 팀 협업, 결제·구독 기능을 만들지 않는다.

핵심 검사·저장·수정·회귀 비교가 안정된 뒤 작은 편의 기능만 추가한다. 제품 범위를 늘려 마무리를 미루지 않는다. 고품질의 기준은 기능 개수보다 정확한 상태, 신뢰할 수 있는 실측, 재현 가능한 흐름, 완성된 사용자 경험이다.

### 19. 완료 기준과 보고 방식

다음이 모두 충족되어야 ‘구현 완료’라고 보고한다.

- 새 환경에서 문서대로 설치·실행 가능.
- 샘플 시작과 사용자 JSON 입력 모두 작동.
- 지원 변수 검증과 실제 fixture 측정이 테스트에서 통과.
- 수정 → 같은 조건 재검사 → 실행 비교가 실제로 작동.
- 로컬 저장 후 재방문·export가 작동.
- 클라우드 adapter·schema·인증·소유권 정책·연결 검증 도구가 준비됨.
- Google adapter·실패 처리·사용량 제한·키 보호가 구현됨.
- 주요 화면의 로딩·실패·빈 상태·작은 화면을 직접 점검함.
- 타입·lint·핵심 테스트·production build 결과가 기록됨.
- Git 커밋이 만들어짐. 불가능한 경우 실제 원인과 필요한 조치가 기록됨.
- API·DB·배포 미연결은 완료 표시와 분리되며 키 입력 후 절차가 바로 실행 가능함.

실제 Google 호출, 클라우드 DB 소유권 검증, 배포 smoke test가 통과한 경우에만 ‘실연결·배포 완료’라고 보고한다. 일부 외부 인증이 필요한 경우 ‘로컬 구현·검증 완료, 외부 연결 대기’처럼 사실에 맞는 상태를 사용한다.

작업 중에는 발견한 문제, 판단, 다음 검증을 짧게 알린다. 선택 가능한 사소한 구현 방식은 직접 결정하고 문서에 남긴다. 반드시 필요한 사용자 답변이 있으면 그 질문만 하고 독립 작업을 계속한다.

최종 답변에는 실행 방법과 경로/URL, 완료한 기능, 검증 결과, 커밋·PR, 남은 외부 연결과 사용자 최소 작업을 짧게 포함한다. 막힌 작업을 포함한 handoff 문서를 연결한다. 가능한 작업을 남겨둔 채 ‘원하면 이어서 할게요’로 마무리하지 않는다.

**지금 바로 기준 md와 작업 폴더를 확인하고, 기술 PoC부터 실제 구현을 시작하라.**
